# 기여 기록 및 협업 가이드

이 문서는 HOOD&SEEK에서 각 팀원의 작업을 GitHub에 정확히 귀속하고, 나중에 프로젝트 회고·대회 제출·포트폴리오 자료로 활용하는 방법을 설명합니다.

Git을 처음 사용한다면 먼저 [HOOD&SEEK Git 시작 가이드](git-start-guide.md)를 따라 저장소, 브랜치, 커밋과 Pull Request의 기본 흐름을 익힙니다.

## 1. 기여 기록은 두 종류입니다

### GitHub가 자동으로 남기는 기록

GitHub는 다음 활동의 계정과 시간을 자동으로 기록합니다.

- 커밋의 작성자(`Author`)와 반영자(`Committer`)
- Pull Request 작성자, 변경 파일, 대화와 수정 과정
- 코드 리뷰 작성자와 승인·변경 요청 내역
- 이슈 작성자, 담당자와 논의 내역
- 기본 브랜치에 반영된 커밋

이 기록이 실제 작업을 입증하는 1차 자료입니다. 작업 브랜치를 병합 후 삭제해도 병합된 커밋과 PR 기록은 남습니다.

### 사람이 설명하기 위해 관리하는 문서

README와 `CONTRIBUTORS.md`는 역할과 결과를 사람이 빠르게 이해하도록 정리하는 2차 자료입니다.

- `README.md`: 현재 프로젝트 구조와 팀 역할
- `CONTRIBUTORS.md`: 개인별 담당 영역, 대표 작업과 PR 링크
- `docs/`: 설계 결정, 리뷰, 시행착오와 회고

Markdown 파일도 Git으로 관리되므로 변경 이력과 `Blame`에서 수정자를 확인할 수 있습니다. 다만 문서에 이름을 적는 것만으로 GitHub 기여도가 자동 생성되지는 않습니다.

## 2. 작업 전 계정 설정

각 팀원은 자신의 GitHub 계정으로 저장소에 접근하고, GitHub 계정에 등록된 이메일을 커밋에 사용해야 합니다.

```bash
git config user.name
git config user.email
```

값이 없거나 다른 사람의 정보라면 이 저장소에서만 설정합니다.

```bash
git config user.name "본인 이름"
git config user.email "GitHub에 등록된 이메일 또는 noreply 이메일"
```

`--global`을 사용하지 않으면 현재 저장소에만 적용됩니다. 공용 PC나 교육장 PC에서는 저장소별 설정을 권장합니다.

커밋 후에는 다음 명령으로 실제 귀속 정보를 확인합니다.

```bash
git show -s --format='Author: %an <%ae>%nCommitter: %cn <%ce>' HEAD
```

GitHub 커밋 페이지에서 프로필 사진과 사용자명이 연결되어 표시되는지도 확인합니다.

## 3. 표준 작업 흐름

### 3.1 최신 `main`에서 개인 작업 브랜치 생성

```bash
git switch main
git pull origin main
git switch -c feat/jaebeom-31-flutter-dashboard
```

권장 브랜치 형식은 `<종류>/<이름>-<이슈번호>-<작업>`입니다. 이슈 번호가 들어가면 PR 본문의 `Closes #번호`와 함께 Projects 보드 카드가 자동으로 따라옵니다.

| 종류 | 용도 | 예시 |
|---|---|---|
| `feat/` | 기능 추가 | `feat/jaebeom-31-flutter-dashboard` |
| `fix/` | 버그 수정 | `fix/jeongin-12-uart-timeout` |
| `docs/` | 문서 변경 | `docs/hyunji-40-risk-policy` |
| `test/` | 테스트 보강 | `test/byungjik-18-smoke-scenario` |

브랜치 이름은 작업자를 알아보기 위한 규칙일 뿐, GitHub 기여도는 커밋 작성자와 PR 작성자 기준으로 귀속됩니다.

### 3.2 의미 있는 단위로 직접 커밋

```bash
git add flutter_app/lib
git commit -m "feat(flutter): 주방 상태 카드 추가"
```

커밋 메시지는 `종류(영역): 작업 결과` 형식을 권장합니다. 결과 문장은 한국어로 씁니다 (CLAUDE.md 작업 규칙). 영역은 `safety_core` `vision` `voice` `flutter` `esp32` `contracts` `profiles` `deploy` `ci` `docs` 중에서 고릅니다.

- `feat(flutter): 팬 단수 요청 버튼 추가`
- `fix(esp32): 명령 3초 끊김 시 fail-safe 진입`
- `test(safety_core): danger 전이 우선순위 검사 추가`
- `docs(contracts): state 메시지 reasons 코드 표 추가`

한 사람이 다른 팀원의 작업까지 자신의 계정으로 대신 커밋하면 GitHub에는 커밋한 사람의 기여로 표시될 수 있습니다. 가능한 한 실제 작성자가 직접 커밋하고 푸시합니다.

### 3.3 본인 계정으로 브랜치 푸시와 PR 생성

```bash
git push -u origin feat/jaebeom-31-flutter-dashboard
```

PR에는 다음 내용을 기록합니다.

1. 작업 목적과 배경
2. 주요 변경 파일과 기능
3. 실행·테스트 방법과 결과
4. 화면 작업이라면 전후 캡처 또는 짧은 영상
5. 미완료 사항과 후속 작업
6. 관련 이슈와 설계 문서 링크

PR은 결과뿐 아니라 검토 과정과 시행착오까지 남기므로 포트폴리오에서 커밋 수보다 강한 작업 증거가 됩니다.

### 3.4 다른 팀원이 리뷰

작성자 외 팀원 1명 이상이 다음을 확인합니다.

- 요구사항과 실제 동작이 일치하는가
- 담당 모듈의 경계를 침범하지 않는가
- 안전 제어 우선순위가 유지되는가
- 테스트와 실패 대응이 충분한가
- 문서와 코드가 함께 갱신되었는가

리뷰 의견은 메신저에서만 합의하지 않고 가능하면 PR에 남깁니다. 그래야 결정 이유와 개선 과정이 프로젝트 기록으로 보존됩니다.

### 3.5 검사 통과 후 `main`에 병합

커밋 기여가 GitHub 프로필에 반영되려면 일반적으로 기본 브랜치인 `main`에 도달해야 합니다.

| 병합 방식 | 기록 특성 | 권장 상황 |
|---|---|---|
| Merge commit | PR의 개별 커밋과 작성자를 그대로 보존 | 여러 작성자의 커밋이나 학습 과정을 보존할 때 |
| Squash and merge | PR 전체를 논리적 커밋 하나로 정리 | 한 명이 수행한 짧은 기능 PR |
| Rebase and merge | 작성자별 커밋을 선형으로 보존 | 커밋이 이미 잘 정리된 경우 |

여러 작성자가 참여한 PR을 squash할 때는 공동 작성자 표기가 최종 커밋에 보존되는지 확인합니다.

## 4. 공동 작업 기록

두 명 이상이 실제로 같은 변경을 공동 작성했다면 커밋 본문에 공동 작성자를 추가할 수 있습니다.

```text
feat(fusion): add critical risk transition

Co-authored-by: 남현지 <GitHub에 등록된 이메일>
Co-authored-by: 임재범 <GitHub에 등록된 이메일>
```

규칙:

- `Co-authored-by:`는 커밋 메시지 마지막에 작성합니다.
- 이름만 적지 않고 GitHub 계정에 연결된 이메일을 사용합니다.
- 단순 리뷰나 조언만 한 경우에는 공동 작성자 대신 PR 리뷰 기록을 사용합니다.
- 실제로 공동 작성하지 않은 사람을 형식적으로 추가하지 않습니다.

다른 팀원이 만든 커밋을 `cherry-pick`하면 원래 `Author`는 유지되고 적용한 사람은 `Committer`로 남습니다. 패치를 대신 적용해야 할 때는 작성자를 임의로 바꾸지 않습니다.

## 5. 팀원별 기여 문서 관리

`CONTRIBUTORS.md`에는 다음만 기록합니다.

- 이름과 확인된 GitHub 사용자명
- 현재 담당 영역
- 실제 병합된 대표 PR
- 구현·설계·테스트 등 구체적인 결과

작업 계획만으로 기여 목록에 넣지 않고, PR이 병합된 뒤 대표 작업을 추가합니다. 역할이 바뀌면 README와 `CONTRIBUTORS.md`를 같은 PR에서 갱신합니다.

추천 작성 예시:

```markdown
| 이름 | GitHub | 담당 | 대표 기여 |
|---|---|---|---|
| 임재범 | [@jaebeom](...) | Flutter UI/HMI | [#1 대시보드 기반 구축](...) |
```

## 6. 비공개 저장소와 포트폴리오

현재 저장소가 비공개라면 저장소에 접근할 수 없는 외부인은 코드, PR과 저장소 이름을 볼 수 없습니다. GitHub 프로필에서 비공개 기여 표시를 켜면 날짜별 기여 횟수는 공개할 수 있지만 세부 내용은 숨겨집니다.

포트폴리오 활용 원칙:

1. 개발 중에는 팀 공식 저장소를 단일 원본으로 유지합니다.
2. PR 본문에 담당 범위, 검증 결과와 화면 자료를 충실히 남깁니다.
3. 대회 종료 후 팀 합의에 따라 저장소 공개 여부를 결정합니다.
4. 공개가 불가능하면 팀 동의를 받은 범위에서 별도의 사례 설명·영상·비식별 데모를 제작합니다.
5. 비공개 코드를 개인 계정에 임의로 복제하거나 공개하지 않습니다.

개인 포크는 소유권이나 공개 권한을 만들어 주지 않습니다. collaborator 권한이 있는 팀원은 공식 저장소의 개인 브랜치와 PR을 사용하는 것을 원칙으로 합니다.

## 7. 기여 기록 체크리스트

### 작업자

- [ ] 내 GitHub 계정과 연결된 이메일로 커밋했는가
- [ ] `main`이 아닌 개인 작업 브랜치를 사용했는가
- [ ] 커밋 메시지가 변경 목적을 설명하는가
- [ ] 본인 계정으로 PR을 생성했는가
- [ ] PR에 테스트 결과와 후속 작업을 기록했는가
- [ ] 역할 변경이 있다면 문서도 갱신했는가

### 리뷰어

- [ ] 코드와 문서의 작성자 표시가 올바른가
- [ ] 자동 검사가 통과했는가
- [ ] 안전·통신·UI의 책임 경계가 유지되는가
- [ ] 공동 작업자의 표기가 필요한가
- [ ] 병합 후 `CONTRIBUTORS.md`에 추가할 대표 기여인가

### 병합 후

- [ ] PR이 `main`에 병합되었는가
- [ ] GitHub 커밋 페이지에서 작성자 계정이 연결되는가
- [ ] 필요하면 작업 브랜치를 삭제했는가
- [ ] README 역할과 `CONTRIBUTORS.md`가 현재 상태와 일치하는가

## 8. 현재 HOOD&SEEK 적용 원칙

- 공식 저장소는 `lambdaramji/HOOD-SEEK`입니다.
- 팀원은 공식 저장소의 개인 작업 브랜치에서 작업합니다.
- `main` 직접 푸시보다 PR과 리뷰를 기본으로 합니다.
- Flutter 변경은 포맷, 정적 분석, 위젯 테스트와 Web 빌드를 통과해야 합니다.
- Pi4는 센서·영상 관측, Pi5는 안전 판단과 중계, ESP32는 팬 fail-safe 집행, Flutter는 사용자 표현을 담당합니다.
- 역할과 대표 기여는 README와 `CONTRIBUTORS.md`에서 관리합니다.
