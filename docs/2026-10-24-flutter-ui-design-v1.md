## 0. 이 문서가 답하는 것

- 현 `flutter_app/lib/screens/dashboard_screen.dart`(969줄, 세로 스크롤·다크·최대폭 1040 [실측 `c7c8328`])는 설계서 §5.4 ①~⑥을 모두 구현했지만, 심사 화면으로는 정보 밀도가 높고 "개발자가 만든" 인상이라는 PM 판단(10/23). 이 문서는 **같은 state·같은 ui_cmd**로 화면만 다시 짠 기준이다.

### 2.3 글꼴 — LG EI [실측 10-23 첨부 zip 분석]

| 가족 | 굵기 | 글리프 | 용도 |
|---|---|---|---|
| LG EI Text | Light·Regular·SemiBold·Bold | 14,042 (한글 11,172) | 본문·UI 전체 |
| LG EI Headline | Thin·Light·Regular·Semibold + VF | 596 (한글 없음) | 핵심 수치(96·44 px)만. 뒤따르는 단위·한글은 Text로 |

**기기(심사 화면)는 LG EI로만 실행한다** (PM 결정 10/24). 파일은 저장소에 넣지 않는다 — LG 브랜드 서체라 재배포 조건 확인 전(R-16, P-010). 그래서 `pubspec.yaml`에 글꼴을 등록하지 않고 **실행 중에 읽는다**.

| 환경 | 동작 |
|---|---|
| 기기 (Pi 5) | PM이 전달한 원본 TTF를 기기 폴더에 두고 `--dart-define=FONT_DIR=<폴더>`로 실행. 앱은 첫 화면 전에 `FontLoader`로 `LG EI Text`·`LG EI Headline`을 등록 |
| 기기 기동 확인 | Flutter 수동 기동(D-046) 명령 앞에 파일 확인을 붙인다. 하나라도 없으면 **기동하지 않고** 빠진 파일명을 출력 → 대체 글꼴로 심사를 치르는 일이 없게 함. 예: `for f in LGEIText-Regular LGEIText-SemiBold LGEIHeadline-Light; do test -f "$FONT_DIR/$f.ttf" \|\| { echo "missing $f.ttf"; exit 1; }; done` (파일 목록은 #112 구현에서 확정) |
| 기기 실행 중 | `FontLoader` 등록이 실패하면(파일 손상·읽기 오류) **Noto Sans KR로 대체해 화면을 그대로 그린다** (PM 결정 10/24). 경고 화면·배너는 없고 로그 한 줄만 남긴다. 앱은 멈추지 않는다 — 안전 표시 화면을 글꼴 때문에 끄지 않는다 |
| CI · 개발 PC | `FONT_DIR` 없음 → Noto Sans KR. `flutter test`·`flutter build web`은 LG EI 없이 통과 |

대체 글꼴 Noto Sans KR은 **앱에 포함한다**(`flutter_app/assets/fonts/`, `pubspec.yaml` 등록). SIL Open Font License 1.1이라 저장소에 넣어도 되고 라이선스 파일을 함께 둔다. 기기가 인터넷 없이 LAN만 쓰므로 `google_fonts`처럼 실행 중 내려받는 방식은 쓰지 않는다. 테마는 `fontFamily: 'LG EI Text'`, `fontFamilyFallback: ['Noto Sans KR']` — LG EI 등록이 실패하면 Flutter가 자동으로 다음 글꼴로 그린다. 기기에 한글 시스템 글꼴이 있는지에 기대지 않는다 [추정 — 확인: Pi 5에서 `fc-list :lang=ko`가 비어 있는지]. 앱 크기가 늘어나는 정도는 #112 구현에서 웨이트 수(Regular·Medium·Bold 3종 권장)로 조절한다.

`pubspec.yaml` 등록을 쓰지 않는 이유: [실측 10/24 임재범, PR #113 리뷰] 앱 사본에 `fonts:` 한 줄을 넣으면 파일이 없는 CI·다른 PC에서 `flutter test`·`flutter build web` 둘 다 `Error: unable to locate asset entry in pubspec.yaml: "assets/fonts/LGEIText-Regular.ttf".`로 멈춘다. 재배포 허용이 확인되면 그때 저장소 추적 + `pubspec` 등록으로 바꾼다.

스플래시 배경 `LG Electronics Gradient 01~04`도 같은 취급(목업 `images/README.txt`).

| 그 외 | 정상 · 모든 센서 작동 중 | 정상 |

기기 무응답(`FAN_NOACK`·`IND_NOACK`)은 hazard를 바꾸지 않고 Core가 `reasons` 맨 뒤에 붙인다(`policy.cpp` 326~327행 [문서]). 그래서 위험·잠금·경고보다 아래에 둔다 — 위험 중 무응답이 겹쳐도 배지는 위험(병직 리뷰 2, PR #114 리뷰).

**수증기는 표시하지 않는다** (PM 결정 10/24). 수증기가 연기와 구분되지 않는 문제가 남아 있고, 앱이 `tsize`로 가르면 앱이 판정하는 것이 된다(D-042 ②). 또 `PM_WARN`만 있을 때 「연기가 아니에요」라고 쓰면 `SMOKE` 확정 전 단계에서 위험한 쪽으로 틀린다. 「정상 · 수증기 감지」, 「수증기예요, 연기가 아니에요」, 그래프 수증기 주석을 쓰지 않으며 `PM_WARN`은 공기 게이지 「연기 있음」과 §4.2 설명 「온도는 정상이고 연기가 조금 있어요」로만 보인다(D-054, #130). T2가 수증기 사유 코드를 계약에 넣으면 그때 다시 정한다.

### 4.2 안전 헤드라인 (reasons[0] 기준, 시스템이 한 일은 과거형 한 문장)

| reasons[0] / 상태 | 헤드라인 | 설명 |
|---|---|---|
| (대기) `present` ∧ `allowed_on` | 조리를 시작해 볼까요? | 인덕션과 음성 명령을 바로 쓸 수 있어요. |
| (대기) `present` ∧ `allowed_on` 거짓 (부팅 유예·쿡탑 무응답) | 곧 조리를 시작할 수 있어요 | 안전 장치가 확인을 마치면 인덕션을 켤 수 있어요. |
| (대기) `absent` | 빈 주방을 안전하게 지키고 있어요 | 자리가 비어 있는 동안에는 반려동물이나 실수로 인덕션이 켜지지 않아요. |
| (대기) `unknown` | 조리대 앞에 서면 시작할 수 있어요 | 안전을 위해 사람이 확인될 때만 인덕션 켜기를 허용해요. |
| (정상) | 안전하게 조리 중입니다 | 온도와 공기 질이 정상 범위예요. |
| `TEMP_MID` (중불) | 중불로 조리 중이에요 | {후드를 n단으로 / 최대로} 켜 두었어요. |
| `TEMP_HIGH` (강불, present) | 강불로 조리 중이에요 | {후드를 n단으로 / 최대로} 올렸어요. 인덕션은 그대로예요. |
| mid 이상 ∧ presence ≠ present | {`ABSENT`→자리를 비우셨어요 / 그 외→조리대 앞에 계신지 확인할 수 없어요} | {온도가 매우 높아 / 연기가 많아 / 불이 켜져 있어 / 안전을 위해} 후드를 최대로 올리고 인덕션은 {n}단까지만 쓰게 했어요. (인덕션이 꺼져 있으면 「… 후드를 최대로 올렸어요.」) |
| `TEMP_DANGER` (warning, 단독) | 조리 온도가 매우 높아요 | 후드를 최대로 올렸어요. 인덕션은 그대로예요. |
| `SMOKE` (warning, 단독) | 연기가 많아요 | 후드를 최대로 올렸어요. 인덕션은 그대로예요. |
| `PM_WARN` (low) | 안전하게 조리 중입니다 | 온도는 정상이고 연기가 조금 있어요. (공기 게이지 「연기 있음」, hazard에 안 씀 — D-054) |
| `TEMP_DANGER` + `SMOKE` (danger, **화재위험**) | 화재 위험을 미리 감지해 인덕션을 껐어요 | 후드가 최대로 환기하고 있어요. 뜨거운 조리 기구는 그대로 두세요. 가운데 창에는 셋째 줄 「연기가 걷히고 온도가 내려가면 확인 후 다시 쓸 수 있어요」 (P-011 §5 — 대피·119 등 화재 발생 가정 문구 금지) |
| `TEMP_ABS` (위험 잠금 중 `SMOKE`만 남으면 「연기가 감지되었어요」) | 온도가 너무 높아요 | 인덕션을 끄고 후드를 최대로 올렸어요. |
| `CAT_NEAR` + locked_cat | 반려동물이 조리 공간에 있어요 | 안전을 위해 인덕션을 잠갔어요. |
| locked_cat (`CAT_NEAR` 없음) | 반려동물 잠금 중이에요 | 조리대 앞에 사람이 오면 잠금이 풀려요. |
| `ACK_WAIT` | 위험이 해소됐어요 | 확인을 누르고 조리대 앞에 계시면 잠금이 풀려요. |
| `UNLOCK_WAIT` | 확인했어요 · 해제 대기 중 | {ABSENT·VISION_STALE→돌아오시면 / 그 외→잠시 뒤} 잠금이 풀려요. |
| `SENSOR_FAULT` | {온도/공기, 둘 다면 센서} 센서가 응답하지 않아요 | 안전을 위해 후드를 최대로 올리고 인덕션을 껐어요. |
| fault ∧ `SENSOR_FAULT` 없음 (profile을 못 읽은 fail-safe) | 안전 장치가 아직 준비되지 않았어요 | 안전을 위해 후드를 최대로 올리고 인덕션을 껐어요. |
| `IND_NOACK` | 인덕션이 응답하지 않아요 | 연결을 확인해 주세요. 그동안 인덕션을 켤 수 없어요. |
| `FAN_NOACK` | 후드가 응답하지 않아요 | 후드 연결을 확인해 주세요. |
| stale | 안전 장치와 연결이 끊겼어요 | 후드는 안전 모드로 계속 돌아가요. 인덕션은 켤 수 없어요. |

| 상태 | 모달 | 디밍 | 원인 카드 테두리 2 px |
|---|---|---|---|
| low / mid / high · present | 없음 | — | 없음 |
| warning · present (과열·과한 연기 단독) | **없음** — 조리 중 방해 금지. 헤드라인·기기 카드만 변화 (리뷰 동의) | — | 온도 카드 |
| high·warning · absent / locked_cat / fault | 우측 770×700 (카메라를 가리지 않음) | 35 % | 카메라(고양이) / 온도 카드(센서) |
| danger / locked_danger (hazard > mid) | 중앙 1040×680, **해제 조건 줄(§4.5) 포함** | 55 % | 카메라(연기) / 온도 카드(고온) |

| `UNLOCK_WAIT` | 같은 모달, 조건 카드만 갱신. 1차 버튼은 「닫기」(ACK는 이미 받음) | 55 % | 없음 |

모달 1차 버튼: 위험 「확인했어요」(닫기만, 상태 변화 없음) · 고양이 창은 「확인」만(누를 수 없는 버튼을 두지 않음 — Core가 조건이 맞으면 푼다, #178) · 부재 「인덕션 끄기」(`IND_SET 0`). **어느 버튼도 잠금을 직접 풀지 않는다**(불변식 ⑨). ACK 버튼 문구에 「잠금 풀기」를 쓰지 않는다 — `ACK_ALERT`는 세 조건 중 하나일 뿐이라 버튼이 직접 푸는 것처럼 읽히면 안 된다(리뷰 ⑤). 대신 조건 카드가 무엇이 남았는지 보여 준다.

### 4.4 음성 카드 (`state.p.voice`)

| voice | 문구 |
|---|---|
| null | 음성으로 시작하기 · "하이 LG, 후드 약풍" (호출어와 명령을 이어서 한 번에) |
| accepted | 요청을 받았어요 · "{intent 문구}" · 지금 {기기} {level}단 · {상대 시각} — Core가 받았다는 뜻이지 물리 동작 완료가 아니다(수현 리뷰 3) |
| accepted=false | "{intent 문구}" — {reason: LOCKED→잠금 중이라 거부됨 / HAZARD→위험 상태라 거부됨 / ABSENT→자리 비움 / IND_NOACK→인덕션 응답 없음 / NO_INTENT→지원하지 않는 명령} |

호출어는 **「하이, 엘지」로 확정** (PM 결정 10/24). 화면 표기는 「하이 LG」. 송신 상태 [문서 PR #107 본문 `4f3b60e`, 10/24]: 하이엘지(SenseVoice) 경로는 **코드상 명시적 `--publish`에서 TCP `voice` 송신이 가능하고, 기본은 발행 끔**이다. 현장 송신은 부정 시험(비명령 36건 + 주변음 300 s에서 실행 0건, #107 PM 결정 A6)과 운영 승인 뒤에 켠다. 「코드로 보낼 수 있음」과 「현장에서 보내도 됨」을 구분한다(수현 리뷰 5). 지원 명령은 `voice` 계약 intent 8종(FAN_SET·FAN_OFF·IND_ON·IND_OFF·IND_UP·IND_DOWN·NONE, voice `v` 2의 IND_SET — D-062)뿐이며 온도·남은 환기 시간·후드 상태 조회는 지원하지 않는다.

intent 문구는 현 `_intentLabel` 유지(FAN_SET value→약/중/강, FAN_OFF, IND_ON/OFF/UP/DOWN). `IND_SET`(D-062, state v 4)은 「인덕션 n단 설정」. 같은 화면의 「후드 n단」과 맞출지는 리뷰 제안으로 남김(§7 #9).

**결과 음성 안내** (#176 · #186, 음원과 문구는 [`assets/audio/results/README.md`](../flutter_app/assets/audio/results/README.md)). 「요청을 받았어요」는 소리로 내지 않고, Core가 확정한 최종 설정만 말한다.

| 조건 | 내는 소리 |
|---|---|
| 새 voice 결과가 `accepted` → 그 뒤 3 s 안 state에서 후드 `fan.requested`가 목표(FAN_OFF는 0)이고 `fan.ack` | 최종 `fan.level`이 목표와 같으면 `RESULT_FAN_N`·`RESULT_FAN_OFF`, 안전 하한(`fan.min`)으로 더 높으면 `RESULT_FAN_MIN_N` |
| 같은 조건에서 인덕션 `induction.ack` ∧ 최종 단수가 바뀜(IND_OFF는 0, IND_SET은 목표 단수와 같음) | `RESULT_IND_N`·`RESULT_IND_OFF` |
| 새 voice 결과가 `NONE` ∧ `NO_INTENT` ∧ 같은 state에 alert 없음 | `RESULT_UNSUPPORTED` 「지원하지 않는 명령입니다.」 한 번 |
| 3 s 안에 맞는 state가 없음, alert가 옴, 연결 끊김 | 내지 않음(기다리던 결과도 버림) |

- `results/` 소리는 기동음·조작음처럼 경고를 끊지 않고, 경고가 나는 동안에는 생략한다. 새 경고는 결과 소리를 끊는다(`gst_clip_player.dart`).
- `ack`는 2 s 안에 장치 링크가 살아 있었다는 뜻이지 요청별 물리 동작 완료가 아니다. voice에 요청 순번이 없어 같은 결과가 연달아 오면 한 번만 난다.

### 4.5 잠금 해제 3조건과 남은 시간 표시 (PM 결정 10/24)

`locked_danger` 해제는 **hazard ≤ mid `P_lock_release_s` 연속 ∧ `ACK_ALERT` ∧ presence=present** 세 조건 AND다(불변식 ⑨, `safety_core/src/policy.cpp` 7단계 [문서]). 잠겨 있는 동안 세 조건을 늘 보여 주고, 무엇이 남아서 안 풀리는지와 **안전 시간이 몇 초 남았는지**를 사용자가 알 수 있게 한다. **앱은 조건을 판정하지도, 시간을 세지도 않는다** — 아래 표는 state 값을 그대로 옮긴 것이다.

#### 4.5.1 state에 더하는 값 — 계약 변경 (PM 승인 10/24, `contract-change`)

지금 state에는 안전 시간의 경과가 없어서 ①을 "확인 중"으로밖에 보일 수 없다. 앱이 직접 시간을 세면 Core와 어긋나고 판정을 중복 구현하게 되므로(CLAUDE.md 「Flutter나 관측 노드에 판단을 중복 구현하지 않습니다」), Core가 남은 시간을 보낸다.

| 필드 | 타입 | 값 | 뜻 |
|---|---|---|---|
| `p.lock_release_left_s` | integer \| null | `lock=locked_danger` ∧ `hazard` ≤ mid이면 `max(0, ceil(P_lock_release_s − 안전 상태 경과 s))`, 그 외 `null` | ①의 남은 초. `0`이면 ① 충족 |
| `p.thresholds.lock_release_s` | number | `profiles/default.json` `P_lock_release_s` 사본 (현재 `10`) | 진행 원의 전체 길이. 판정에 쓰지 않음(기존 `thresholds`와 같은 표시용) |

- Core 계산 근거: `safe_since_ms_`는 `lock_=locked_danger ∧ hazard_ ≤ mid`인 첫 tick에 잡히고 hazard가 mid를 넘으면 지워진다(`policy.cpp` 7단계 [문서]). 남은 시간은 이 값에서만 계산한다.
- `ceil`로 올림해 `0`은 실제로 시간이 다 찼을 때만 나온다. state 2 Hz라 표시는 0.5 s 단위로 갱신된다.
- 변경 범위(계약 규칙 — `contracts/README.md` 「변경 규칙」): `contracts/state.schema.json`·`examples/state*.json`·state `v` 1→2 · Core `policy.*` 계산(T2)·`message.cpp` 송신(T1) · Flutter `lib/data/core_state.dart` 수신(T6, `v` 상수 검사). 다른 수신자는 [문서] vision-node가 state 줄을 읽고 버리고(`vision_node/src/link.cpp` 83행) voice-node는 해석하지 않아(`voice_node/src/voice_tcp.cpp` 196행) 파서 변경이 없다 — PR #107의 관측 도구가 state를 읽는지는 계약 PR에서 확인. **`v`는 state만 올린다** (#116 재범 안, PM 결정 10/24): 스키마는 메시지마다 `v`를 따로 두므로(`contracts/*.schema.json` `"v": { "const": 1 }`) state만 2로 올리고 vision·voice·ui_cmd·hello는 1 그대로 둔다. Core 입력 검사(`safety_core/src/message.cpp` 151행)는 바꾸지 않는다 — 바꾸면 v1 입력을 모두 버려 2 s 뒤 presence=unknown → 인덕션 켜기 거부로 시연이 멈춘다(병직 리뷰 3). Flutter는 state v1·v2를 모두 받아 Pi 4·Pi 5 배포 순서와 상관없게 하고, v1이면 남은 초를 아래 "필드 없음" 열대로 그린다. `contracts/README.md` 공통 envelope 설명에 「`v`는 메시지 종류별」을 더한다. **이 PR(#113, 문서)과 분리한 별도 PR**로 낸다 — 이슈 #116, 라벨 `contract-change`.
- 계약 PR이 병합되기 전 앱은 ①을 아래 "필드 없음" 열대로 그린다.

#### 4.5.2 조건별 표시

| 조건 (화면 이름) | 충족 (그린 ✓) | 진행 중 (그레이 + 진행 원) | 미충족 (레드 !) | 필드 없음(계약 PR 전) |
|---|---|---|---|---|
| ① 안전한 상태 유지 | `lock_release_left_s = 0` — 「안정 시간을 채웠어요」 | `> 0` — 「n초 남음 · {lock_release_s}초 중」, 원은 지난 비율 | `null` ∧ `hazard` > mid — 「위험 진행 중」 | 잠김 ∧ ≤ mid이면 「안정될 때까지 지켜보는 중」(회전) |
| ② 위험 확인 | `UNLOCK_WAIT`∈reasons — 「확인했어요」 | — | `ACK_WAIT`∈reasons — 「아래 버튼을 눌러 주세요」 | 같음 |
| ③ 조리대 앞 사람 | `presence=present` — 「주방에 계세요」 | — | `absent` — 「자리를 비우셨어요」 / `unknown` — 「카메라 확인 중」 | 같음 |

`hazard` > mid일 때 ②는 그레이 「위험이 내려간 뒤 누를 수 있어요」(이때 받은 ACK는 Core가 버림).

| 화면 | 표시 | 목업 |
|---|---|---|
| 위험 모달 (hazard > mid) | 버튼 위 한 줄 알약 3개 | `AlertSmoke.html` (위험 진행 중 · 확인 대기 · 자리 비움) |
| ACK·해제 대기 모달 | 조건 카드 3장 + 「세 가지가 모두 충족되면 자동으로 풀려요」. 남은 조건이 하나면 설명을 「남은 조건은 하나예요」로 | `AckWait.html`(①7초 남음 · ②미충족 · ③충족 = 1/3), `UnlockWait.html`(①②충족 · ③자리 비움 = 2/3) |
| 모달을 닫은 뒤 인덕션 카드 | 막대 3칸(조건 색) + 「잠금 해제 조건 n/3 충족 · n초 남음」, 누르면 모달 다시 열림 | `AckWait`·`UnlockWait` 하단 카드 |

## 6. 음성 오버레이 (C1~C3) — 한 문장 발화 구조 (수현 리뷰 10/24 반영)

호출어는 「하이, 엘지」 (PM 결정 10/24). 현재 voice-node 구조는 [문서 PR #107 본문·수현 리뷰 10/24] **ReSpeaker → Silero VAD → 발화 종료(최대 4 s) → SenseVoice 전체 전사 → 호출어 확인 → 명령 판정 → (발행 켜짐이면) Core 송신**이다. 별도 음향 호출어 검출기·호출 후 다음 발화 대기·부분 전사가 없으므로 사용자는 **호출어와 명령을 이어서 한 번에** 말한다(「하이 LG, 후드 약풍」). 「하이엘지 인식됨 → 이제 말씀하세요」 식의 중간 반응은 그리지 않는다. 이번 범위에 TTS·호출 응답음·별도 호출어 검출기는 넣지 않는다.

| 상황 | 일반 사용자 화면 | 데이터 |
|---|---|---|
| 대기 | 음성 카드에 짧은 예시 「하이 LG, 후드 약풍」 (§4.4) | — |
| 주변 대화·호출어 미확인 발화·그 전사 과정 | **기본 화면 유지.** 입력 레벨·「분석 중」·팝업 없음 — 주변 대화·TV에도 VAD·ASR이 돌기 때문 | — |
| 전사 뒤 호출어가 확인된 요청 (C1) | 해석한 명령 + 전달/만료/실패 상태를 하단 시트로 | **T5 → T6 Pi 5 로컬 경로 — 형식 합의됨(#120, 재범·수현 10/24), 구현은 시연 뒤.** 루프백 `127.0.0.1:7421` JSONL, voice-node가 서버·Flutter가 클라이언트. `utterance`: `session`(노드가 뜰 때마다 새 값)+`id`(그 안의 발화 번호, Core `seq`와 별개), `intent`·`value`, `delivery`(`sent` · `not_published` · `send_failed` · `expired` — `sent`는 소켓 쓰기 완료이지 Core 수락이 아님). `status`: 1 s마다 `mode`(`observe` · `publish`) · `core`(`connected` · `disconnected` · `not_configured`) · `mic`(`ready` · `opening` · `error`), 3 s 못 받으면 노드 연결 이상. 원문·호출어 없는 발화는 보내지 않고, Core 결과와 추정해 짝짓지 않음. 구현 전에는 이 화면 없음 |
| 호출어는 확인됐지만 NONE | 「이 말씀으로는 동작하지 않았어요」 중립 안내 | 같은 로컬 경로(구현 뒤). 지금은 Core의 새 `NONE`·`NO_INTENT` 결과를 경고 창이 없으면 C3 거부 시트로 보이고, alert가 없을 때 「지원하지 않는 명령입니다」 안내 음성도 냄(#186, D-062). 같은 결과가 이어지면 구분하지 못하는 한계는 그대로 |
| Core 결과 도착 — 수락 (C2) | 블루 체크 + 「요청을 받았어요」 + intent 문구(예: 「후드 중풍」) + **지금 {기기} {level}단**, 2 s 뒤 닫힘. 보조 문구 「안전 장치가 요청을 받았어요 · 실제 단수는 안전 하한을 따라요」 — 요청보다 `fan.min`이 높으면 실제 단수가 다를 수 있어서(불변식 ②, 재범 #113 리뷰). **호출어 확인 표식·인식 원문은 없음** — `state.p.voice`는 `last_intent/value/accepted/reason`만 줌 | `state.p.voice.accepted=true` + `fan`/`induction` |
| Core 결과 도착 — 거부 (C3) | 자물쇠(레드) + 「지금은 할 수 없어요」 + 이유 + 지원 명령 칩. 호출어 확인 표식 없음(C2와 같음) | `state.p.voice.accepted=false` + `reason` |

규칙:
- **「지금 처리한 요청」과 「Core의 마지막 결과」는 별개다.** 예전 `state.voice`를 새 요청의 응답처럼 보이지 않는다. 같은 intent·value·accepted·reason이 반복되면 새 시트를 구분하지 못하는 것은 `state.voice`에 명령 식별자가 없는 현 계약의 한계이고, 식별자 추가는 후속 계약 작업이다.
- TCP 송신 성공·관측 후보·Core 수락은 **물리 동작 완료가 아니다.** 「실행했어요」·「후드를 올렸어요」를 쓰지 않는다. 실제 단수는 `state.fan.level`·`induction.level`로 따로 보인다.
- **X·바깥 탭·시트 닫기는 표시만 닫는다.** 상주 노드 종료·마이크 중지·이미 전달된 명령 취소가 아니다.
- UI 자동 닫힘 시간(수락 시트 2 s, C1 시트는 무조작 4 s 제안)은 **UI 값**이며 VAD 최대 발화 4 s와 무관하다.
- 입력 레벨·최초/최종 전사 원문·처리 시간·DROP/타임아웃 상세는 **진단 화면**에만 둔다. 부분 텍스트나 인식률을 만들어 표시하지 않는다. 현재 진단용 웹 페이지는 Flutter용 로컬 IPC가 아니다.
- Core 연결만으로 마이크 정상·준비 완료를 추정하지 않는다. 노드 연결 이상은 로컬 경로 `status`를 구현한 뒤 별도로 표시한다(#120).
- Flutter는 마이크를 열거나 ASR·intent를 다시 판단하지 않는다(불변식 ④와 같은 이유). 위험 모달이 떠 있으면 시트 대신 모달 아래 배너로 축소.
- 로컬 경로 형식은 #120으로 합의했다(카메라 영상 §3.2와 같은 Pi 5 루프백 방식). C1을 구현하기 전에는 결과 시트 C2·C3만 쓴다(§4.6).
