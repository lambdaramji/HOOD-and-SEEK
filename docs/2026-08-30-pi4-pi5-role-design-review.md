## 한 줄

「Pi4가 보고, Pi5가 판단하고, Flutter는 만지지 않고, ESP32가 팬을 집행한다」는 맞다. 약한 지점은 센서와 판단·팬이 랜선을 사이에 둔다는 것이다. 케이블이 빠지면 온도를 쥔 Pi4는 아무것도 못하고, 팬은 ESP32 3초 fail-safe만 남는다.

| | 판정 |
|---|---|
| 논리 경계 (관측 / 판단 / 집행 / 표시) | 맞음 |
| 현행 보드 매핑 | ATLAS·화면에 맞춘 타협 |
| P-009 재배치 | 미결 |

## 바꿔서는 안 되는 논리

보드가 바뀌어도 아래 네 줄은 유지한다. P-009도 이 경계를 뒤집지 않고, 판단 프로세스만 Pi4로 옮긴다.

| 계층 | 하는 일 | 하면 안 되는 일 |
|---|---|---|
| 관측 (카메라·I2C) | 숫자·bbox·재실 후보만 발행 | 인덕션을 직접 잠그거나 팬 단수를 확정 |
| 판단 (`SafetyPolicy`) | 우선순위대로 단계·최소 팬·잠금 후보 | YOLO 한 프레임을 그대로 차단으로 승격 |
| 집행 (ESP32) | PWM과 serial timeout 3단 | 정책을 해석하거나 JSON을 파싱 |
| 표시 (Flutter) | 확정 상태 표시, 팬 요청만 | 잠금 해제, 임계값 변경, 정책 재계산 |

현재 코드는 이 경계를 지킨다. 정책은 `packages/hood_seek_protocol` 한곳이고 Flutter는 `evaluate`를 호출하지 않는다. Pi4 `consecutive_hits`를 믿지 않고 Pi5 `PetAccessTracker`가 시간축을 다시 계산한다. 고양이 감지는 사용자 부재와 함께일 때만 잠금 후보가 된다.

## 현행 배치가 생긴 이유

ATLAS는 Headless(Pi4)와 Video(Pi5)를 쓴다. 화면·음성·인덕션 D-Bus는 Video 쪽에 적혀 있고, I2C는 Headless 쪽에 맞다. 화면 보드가 죽어도 센서 보드가 남도록 둘로 나눈 것도 맞다.

```text
Pi4 (Headless)  센서·비전 발행  ──MQTT──▶  Pi5 (Video)  정책·Flutter·broker
                                                     └──USB──▶ ESP32 팬
```

비전(무겁고 비결정)과 판단(가볍고 결정론)이 다른 보드인 것은 맞다. **센서와 판단이 다른 보드인 것**이 약점이다. 조리면 온도는 Pi4 I2C에 있고 팬 USB는 Pi5에 있어, 안전 루프에 스위치·랜선·broker가 들어간다. 랜선 장애 시 정책은 `offline`만 할 수 있고 실제 온도로 계속 판단하지 못한다.

「라즈4 = 센서, 라즈5 = 두뇌+화면」은 데모·대회 프로파일에 맞다. 주방 안전 제품으로 보면 「센서 옆에 두뇌, 무거운 AI·화면은 옆 보드」가 더 정석이다. 둘 다 틀린 설계가 아니라 최적화 축이 다르다.

## 두 매핑

| | A안 · 지금 코드·문서 | B안 · P-009 |
|---|---|---|
| Pi4 | 센서·비전 발행 | 센서 + `SafetyPolicy` + ESP32 + mosquitto |
| Pi5 | 정책·UI·broker·ESP32 | 카메라 YOLO + Flutter + 음성 |
| 랜선 끊김 | 팬 3단(ESP32)만. 온도 판단 정지 | 온도·PM·팬은 계속. 재실·고양이는 별도 규칙 |
| 계약 | 유지 | `person_present` 분리, topic 이름, `schema_version` 2 |
| 전제 | 없음 | Headless Dart AOT, 카메라 USB가 Pi5에 닿음 |

B안에서 mosquitto를 Pi5에 두면 센서→판단이 다시 랜선을 탄다. 그때는 A보다 나빠지므로, 재배치한다면 broker는 Pi4로 옮긴다.

### B안이 만능이 아닌 이유

| 걸림돌 | 왜 중요한가 |
|---|---|
| Dart AOT on ATLAS Headless | 안 되면 정책을 C++로 복제하게 된다. 단일 진실 공급원 규칙과 충돌 |
| mosquitto를 Pi4로 | broker가 Pi5에 남으면 재배치 의미가 사라짐 |
| 인덕션 D-Bus는 Video(Pi5) | 팬은 Pi4, 잠금은 Pi5로 갈라짐. 데모가 가상이면 참을 수 있음 |
| 카메라 케이블·화각 | 후드 탑뷰 USB를 Pi5까지 뽑을 수 있어야 함 |
| 비전 두절 시 재실 | 부재 간주면 오경보, 재실 간주면 고양이·부재 고온 침묵 |

실측 보탬(확정 아님): [김병직 실기기 조사](../inbox/김병직/2026-08-30-device-survey-and-vision-test.md)에 따르면 `VisionService1`은 Pi5에만 있다. 성능 이전에 **비전 플랫폼 경로가 보드마다 다르다.** P-009를 닫는 근거는 아니고, B안 쪽 실측이다.

## ESP32

맞다. 팬 PWM과 timeout을 리눅스 보드에 두지 않은 것이 이중화의 핵심이다. A든 B든 ESP32는 판단하는 보드 USB에 붙이면 된다. 인덕션까지 릴레이로 가져갈지는 P-009 결정 항목 6이다.

3초 timeout은 대회 규격 인용이 아니라 팀 내부 값이다. 두 계층을 겹친다는 의도만 유지하면 숫자는 조정할 수 있다.

## 구현 전에 고를 것

P-009 결정권자는 현지(안전 경계)·정인(배선)이다. 이 문서는 A를 폐기하거나 B를 채택하지 않는다.

- **A를 유지**하면 랜선 장애는 ESP32 팬 3단으로 설명하고, 그때 온도 연속 판단은 포기한다고 명시한다.
- **B로 가면** Dart Linux ARM64 독립 실행·배포, ESP32 Pi4 시험 연결, 카메라 Pi5 연결, MLX90640·SPS30 동시 polling baseline이 확인되고 현지가 safety policy를 승인한 뒤에만 드라이버를 심는다. 이 중 하나라도 빠지면 구현 병합이 아니라 선행 검증을 계속한다. 카메라 폼팩터는 2026-09-20 실측으로 채워졌고, Dart AOT·ESP32·동시 polling은 아직이다.

선택 전에 Pi4에 I2C나 YOLO를 넣지 않는 편이 싸다. 지금은 스텁이라 이전 비용이 거의 없다.

## 이 문서가 다루지 않는 것

임계값 숫자, 카메라 기종(P-001, 실측은 HD-3000), 모델 확정(P-006), Flutter `pet_access_confirmed` 표시는 별건이다.
