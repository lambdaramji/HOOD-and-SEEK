## 확정된 방향

- [문서·사용자 2026-10-26] 「요청을 받았어요」를 음성으로 읽지 않는다. 처리 뒤 결과가 어떻게 됐는지 말한다. #169에서 제안했던 요청 수락형 8문구는 이 추가 요청으로 대체한다. 현재 팝업의 글귀를 그대로 TTS로 옮기는 방식은 사용하지 않는다.
- [문서·코드] `state.voice.accepted`만으로 최종 단수를 확정하지 않는다. `FanState.level/requested/min/ack`, `InductionState.level/ack`와 최신 결과를 확인해 문구를 고르는 연동을 재범 담당 검토 대상으로 둔다.
- [문서·범위] #169에서 검토받은 기동음·터치음·4회 WARNING 코드는 유지한다. 이번에는 사전 제작 음원·manifest·조건표만 추가하며 Flutter 실행 코드·Core·계약·음성노드·현장 앱을 바꾸지 않는다.

## 음원

[문서] 결과값을 말하는 8개(후드·인덕션 각각 0~3단)와 후드 안전 하한 보정을 설명하는 3개다. 상태별 문구·길이·파일은 [음원 목록](../../flutter_app/assets/audio/results/README.md), 해시·제작 설정은 [manifest](../../flutter_app/assets/audio/results/manifest.json)에 있다.

| 예시 결과 | 안내 |
|---|---|
| 후드 최종 3단·ACK 확인 | 후드를 강풍으로 설정했어요. |
| 후드 최종 0단·ACK 확인 | 후드가 꺼졌어요. |
| 인덕션 최종 0단·ACK 확인 | 인덕션이 꺼졌어요. |
| 요청 0단이지만 안전 최소 3단으로 유지·ACK 확인 | 안전을 위해 후드를 강풍으로 유지하고 있어요. |
| 수락만 받음·응답 미확인·끊김 | 완료 음성 생략 |

- [문서·설계] 「올렸어요」는 이전 값과의 방향 확인이 더 필요하므로 공통 문구를 「설정했어요」로 해 최종값을 정확히 알린다. 단순 수락 문구는 녹음하지 않았다.
- [문서·제약] 완료는 장치가 ACK한 설정값을 기준으로 한다. 회전수·가열 전류 별도 계측을 뜻하지 않으며 쿡탑은 ESP32 시뮬레이터다. 실제 값이 요청과 다르면 실제 값과 안전 유지 결과를 안내한다.
- [문서·제약] `state.voice`에 요청별 ID가 없어 동일 명령 연속·동시 제어를 정확히 대응시키는 한계는 남는다. 실행 코드 연결은 최신 상태·만료·경고 우선순위와 함께 검토해야 한다.

## 제작과 검사

- [문서·제작] 기존 Q3 E2의 자체 합성 참조와 동일 Qwen3-TTS Base 8bit를 재사용했다. AI 합성 음성이며 외부 사람 녹음·Typecast를 쓰지 않았다. 런타임에는 모델을 넣지 않고 WAV만 사용한다.
- [실측·2026-10-26 Mac] Python/MLX 로컬 합성 뒤 48 kHz·mono·PCM16으로 변환, −19 LUFS 목표 정규화·약한 말끝 감쇠. 11/11 유한 샘플·클리핑 0·sha256 일치.
- [실측·2026-10-26 Mac] SenseVoiceSmall INT8 ko/ITN, 파일 전체 자동 전사. 공백·문장부호 제외 10/11이 문구와 일치하고 나머지는 후드의 모음 표기 차이였다. 이것을 사람 청취 합격이나 실시간 명령 성공률로 집계하지 않는다.
- [실측] 이번 11개는 별도 실제 재유입 110회를 완료했다(아래). #137의 70회나 #169 차임 20회를 재사용한 결과가 아니다. 사용자 현장 청취는 확인했으며 PM의 음색·문구 승인과 Flutter 결과 연결·실기는 별도다.

## PM 조건 ② 실제 ReSpeaker 재유입 110회 — 2026-10-26

- [실측] #169 병합 뒤 현장 사용 가능 확인을 받고, 원래 11개 WAV를 각각 10회 재생했다. 파일은 `f4515e3` 및 기존 manifest/SHA256SUMS와 모두 동일하다. 후드 문구를 환기로 바꾸거나 파서·문턱을 바꾸지 않았다.
- [실측] 현재 voice 실행본 `70839f9c...64d43a1`, SenseVoiceSmall INT8 ko/ITN·ASR CPU4·VAD CPU1·하이엘지 진입 경로로 시험했다. 음성 서비스만 잠시 관측 모드로 두고 별도 폴더에서 GStreamer 기본 pulsesink를 사용했다. 운영 앱·Core·비전은 변경하지 않았다.

| 항목 | 결과 |
|---|---:|
| 음원별 완전 재생 | 11개 각각 10회, 총 110회 |
| USB 출력 경로·Playback Running·재생 종료 코드 0 | 110/110 |
| 매 재생 전 자체 PID의 ReSpeaker 입력 확인 | 110/110 |
| NONE 포함 전체 후보 / 송신 | **0 / 0** |
| ASR 종료 집계 | 94회 |
| 보존된 개별 ASR 기록 | 93회, 모두 DROP |
| 보존되지 않은 개별 ASR 기록 | 1회 |

| 비정상 재시작 | 0 |
| 첫 재생 시작→마지막 종료 | 623.9초 |

- [실측·집계 근거] 중간 스냅샷과 종료 저널을 합쳐 개별 ASR 93개를 보존했다. 종료 시 조회본에는 초반 일부가 없었고, 전체 94개 중 1개는 원문이 남지 않았다. 원문을 복원했다고 쓰지 않는다. **종료 시 전체 누적 candidates=0·transmitted=0**이며, NONE도 candidates를 올리는 현재 코드이므로 PM의 NONE 포함 후보 0 기준을 충족했다.
- [실측·한계] 4초 초과 폐기 7건도 그대로 기록한다. 원인은 이 시험에서 확정하지 않았다. 110개 각각이 별도 ASR로 끝났다는 뜻이 아니며, 일반 명령 인식 성공률로 집계하지 않는다.
- [실측] 사용자가 실제 ReSpeaker에서 결과 안내가 들렸음을 확인했다. 출력 장치·음량은 시험 전후 같고, 시험 뒤 원래 발행 켜짐·ReSpeaker 입력·capture_ready·무기한 기동으로 복구했다. 원음 PCM은 저장하지 않았다.
- [문서] 원문 전사·시각별 기기 로그·IP·기기 식별자·개인 경로는 비공개 증거로만 보존한다. [집계 JSON](2026-10-26-voice-result-reentry110.json)과 [sha256](2026-10-26-voice-result-reentry110.sha256)에 공개 가능한 결과·파일 해시를 기록했다.

## PM 사전 파서 검사와 현행 경로 비교

- [실측·Mac, 소스 `abf77c3`] 같은 11개 문구를 비교하면 `parse_command` 직접 호출은 7 NONE·4 제외로 PM 사전 결과가 재현된다. 실제 진입점 `hi_lg::classify`는 원문 11/11 DROP이고, 파일 전체 SenseVoice 전사 11개도 11/11 DROP이다.
- [문서·코드] `audio_observer.cpp` SenseVoice 분기는 `hi_lg::classify`의 호출어 게이트를 먼저 거친다. 통과 뒤 명령 본문 문법 일부에 `parse_command`를 재사용한다. 호출어 게이트 없이 `parse_command`만 호출한 결과를 실제 SenseVoice 진입 결과로 적용하지 않는다. 후보 카운터는 intent가 DROP이 아닐 때 증가하므로 NONE도 포함한다.
- [실측·결론] 문자열 사전 검사를 실기 합격으로 대체하지 않고 위 별도 110회를 수행했다. 실기 후보가 0이어서 이번 문구를 바꿀 조건은 발생하지 않았다. 음원 11개는 원본을 유지한다.
