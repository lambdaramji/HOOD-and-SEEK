## 요약과 근거

[실측] 녹음 파일 업로드가 아닌 실제 상주 입력에서 필수 명령 최초 **24/25 = 96%**, 비명령 **실행 후보0/30**이었다. 비명령은 DROP15·NONE15이고, 55문항의 의도 정답 일치는 **54/55 = 98.1818…%**다. 전사 WER/CER·화자 독립 정확도·실제 집행률이 아니다. 근거: [집계 JSON](measurements/2026-10-24-hi-lg-live55.json), [문항 대조 JSONL](measurements/2026-10-24-hi-lg-live55-trials.jsonl), [원문 이벤트](measurements/2026-10-24-hi-lg-live55-events.log).

[실측] `불 세기`를 정식 화력 대상 후보에 추가한 뒤 기존55문항·사람 재시도1건의 intent/value는56/56 그대로였고, 이후 실패한 `불 새이·불색이·불색기` 전사7건은 텍스트 재입력에서0/7→7/7로 복구됐다. 새 녹음·ASR 재실행 결과는 아니다. 근거: [7건 전사와 전후 판정](measurements/2026-10-24-hi-lg-segi-text-replay.json), `voice_node/src/hi_lg_classifier.h::fallback`.

[사용자 전달 승인] 사용자는 2026-10-24에 “5분 소음/무음 측정은 생략으로 할게. 승인 받음”이라고 전달했다. 이번 PR 검토 범위에서는 **생략·미측정**으로 기록한다. 300초 시험 합격·오탐0건으로 보고하지 않으며, 중간 대기 시간을 합산해 대체하지 않는다. 일반 시험 도구의 기본300초 조건은 유지한다. 근거: 이번 작업 요청 원문, 집계 JSON의 `silence_noise_waiver`.

[후속 실측] 위 문장은55문항 종료 당시의 경위다. 이후 사용자 요청으로 [조용150초·팬/유튜브150초](2026-10-24-voice-ambient300-validation.md)를 별도 실제 측정했고 실행 후보0건이었다. 현재 결과는 후속 보고서를 우선하며, 당시의 생략 승인이나55문항 성적을 소급 변경하지 않는다.

## 실행 구성과 시험 조건

[문서/실측] 실행 흐름은 ReSpeaker Lite → PulseAudio/GStreamer 16kHz mono → 스트리밍 Silero VAD → 상주 SenseVoiceSmall INT8 → 하이엘지 확인 → 대상/동작 토큰 분류 → 관측 로그다. 실제 TCP voice 발행은 꺼져 있고 SenseVoice의 `--publish`는 거부한다. 근거: `voice_node/src/audio_observer.cpp`, 원문 이벤트의 `mode=observation_only`, 집계 JSON.

| 항목 | 이번 실시간 시험 |
|---|---|
| 화자 | 이수현 — 사용자 확인 |
| 팬 | 꺼짐 — 사용자 확인 |
| 거리 | 약30cm로 시작, 중간에1m 이상으로 변경 — 전환 문항 미기록 |
| 주변 소음 | 별도 종류·레벨 미기록 |
| ASR | SenseVoiceSmall INT8 / ko·ITN·greedy / CPU4 / 모델1회 로딩 |
| VAD | CPU1 / 32ms 프레임 / 시작224ms·종료544ms·앞992ms / 발화4초·총 버퍼6초 |
| 문턱 | 활성어0.60·대상0.60·동작0.70·서로 다른 intent 차이0.10 |
| 품질 | `conf=unavailable quality=uncalibrated` — 유사도는 보정된 ASR 확률이 아님 |
| 후드 켜기 | 사용자 선택 기본값 FAN_SET(1), 인덕션 켜기는 인덕션 명시 |
| 시험 실행본 SHA256 | `7eb1d0840d0edc3f5e30605bc1c64827a5e72e891cbe45f4d3e59fc1b5ee5e87` |

[문서] 위 시각은 화면이 결과를 받은 시각이며 사람의 발화 시작·끝 시각이 아니다. 원음 저장을 켜지 않아 실제 발화 끝 기준3초나 음소 잘림을 사후 확정할 수 없다. 거리가 바뀌어도 결과를 삭제하지 않지만 거리별 성공률·목소리 차이로 분리하지 않는다. 근거: `voice_node/tools/live_observer.py::consume`, 사용자 조건 답변, 집계 JSON의 `limits`.

## 최초 25회와 비명령 30회

| 필수 기능 | 최초 일치 | 실패 |
|---|---:|---|
| 강풍 FAN_SET(3) | 5/5 | 없음 |
| 중풍 FAN_SET(2) | 5/5 | 없음 |
| 약풍 FAN_SET(1) | 5/5 | 없음 |
| 팬 끄기 FAN_OFF | 5/5 | 없음 |
| 인덕션 끄기 IND_OFF | 4/5 | P15 꺼→거, NONE |
| 합계 | 24/25 | 재시도 제외 |

[실측] 비명령 N01~N30은 ASR index37~66에 문장·순서가 대응한다. 필수 최초는 index67~81·83~92다. index82는 P15를 사람이 다시 말한 재시도임을 사용자가 확인했으며 최초 분모에서 제외했다. 앞선 임의 명령·잡담과 index93 이후 발화도55문항 성적에서 제외했다. 근거: 문항 대조 JSONL, [원래 시험표](2026-10-24-hi-lg-live55-test-list.md).

[실측] P15의 최초 전사는 `하이엘지 후드 인덕션 거.`이고 `intent=NONE parser_reason=no_explicit_action_or_level`이었다. 활성어 유사도1, `asr_ms=425 end_to_intent_ms=977 expired=0`이므로 호출어·타임아웃 실패가 아니다. 11:15:52의 재시도는 `하이엘지 후드 인덕션 꺼.` → IND_OFF였다. 최초 성공을25/25로 바꾸지 않았다. 근거: 원문 ASR81·82, 문항 대조 P15·P15-R1.

[실측] 비명령30개는 전사 결과가 모두 존재하며 DROP15·NONE15, 실행 후보0건이다. 실제 송신0건은 발행 차단 결과이고 부정 시험의 성공 근거는 실행 후보0건이다. 55문항 구간에서 잘못된 실행 intent·4초 초과·기한 만료는 없었다. 시험 전에 있었던 `max4s`1건은 별도 기록이며55문항 결과에 섞지 않았다. 근거: 원문 이벤트·집계 JSON.

| 시간 지표 | 필수25회 | 비명령30회 |
|---|---:|---:|
| ASR 계산 최소~최대 | 212~537ms | 190~680ms |
| ASR 계산 평균 | 405.44ms | 430.43333333333334ms |
| VAD 종료 기준 판정 추정 최소~최대 | 765~1087ms | 746~1230ms |
| 같은 추정 평균 | 957.24ms | 982ms |

[문서/실측] 필수25개 판정 추정값은 모두3초 이내지만1개는 NONE이다. 정확한 명령 후보가3초 추정 이내 나온 최초 시도는24/25다. 실제 발화 끝→송신·Core 수락·하드웨어 시간으로 해석하지 않는다. 근거: `end_to_intent_ms`의 계산식은 `audio_observer.cpp`, 개별 시간은 문항 대조 JSONL.

## VAD CPU1과 입력 소비 개선

[실측] 이전 VAD CPU4에서는 ASR가 없던12.017초에3.84초 입력을 처리했다(31.95%). CPU1 구성은 ASR1회를 포함한12.013991708052345초에11.52초를 처리했다(95.8881966955142%). 프레임 로그는10프레임 단위이고 ASR 중 입력을 버리는 기존 방침이 있으므로 샘플 단위 유실률로 부르지 않는다. 근거: 작업 PC에 보존한 입력 진단 JSON·처리량 기록; 시험 구성 변경과 관측 로그는 이 문서의 이벤트·집계 JSON.

[실측] 같은39.968초 원음의 Pi5 VAD1/4스레드 대조에서 구간 경계는 같았다. 프레임 계산 평균은 각각0.4185101017/1.896772629ms, 최댓값은1.582592/216.839685ms였다. 4스레드의 긴 프레임 지연을 피하려 공통 VAD를1스레드로 바꿨으며 ASR CPU4는 유지했다. 전력 측정이나 동일 조건의 idle CPU 시험이 아니다. 근거: 작업 PC의 Pi5 프레임 대조 원문, `audio_observer.cpp`의 `vad_params.n_threads`와 `vad_threads` 로그.

## 불 세기 대상 후보 보완

[문서/실측] 기존 후보는 화력·불·세기와 접두 대상 조합이고 `불세기`가 없었다. `색이↔세기` 자모 유사도0.75임에도 `불색이`의 기존 최선 대상 점수는0.50으로 문턱0.60에 미달했다. 정상 `불세기`도 다른 후보와의0.625로 겨우 통과했다. `불세기`를 후보로 추가하면 `불색이`는0.875, `불세기이`는0.666666…가 된다. 단어·동작·호출어 문턱은 바꾸지 않았다. 근거: `hi_lg_classifier.h::sim/target_sim/fallback`, 7건 전후 재입력 결과.

[문서] 이 변경은 `색이`라는 단어를 모든 문장에서 `세기`로 치환하지 않는다. 호출어 뒤의 단일 명령 전체에서 올려/내려/줄여 등 동작을 추출한 뒤 화력 대상 후보로 비교한다. 부정·질문·인용·복합·상태 거절 검사는 앞서 유지된다. 호출어 없이 `불쎄기`만 말한 DROP은 이 문제의 실패 건수로 세지 않는다. 근거: `classify_body`, `semantic`, `fallback`, 실행 검사.

## 현지·정인·재범 검토 요청 — 구현하지 않음

[제안/합의 필요] `후드1단으로 내려줘`와 `후드3단으로 올려줘`는 목표 단수+방향 요청으로 해석하고, voice-node는 의미만 추출하며 **Core가 적용 직전 상태와 비교**하는 방식을 제안한다. 인식 도중 터치나 안전 상태가 바뀌면 음성노드의 과거 상태만으로 허용 여부를 결정할 수 없기 때문이다. 검증 방법: 같은 요청을 Core 입력에 넣기 직전 상태·터치 명령 순서를 바꾸어 방향 검사를 시험한다. 담당 근거: `.github/CODEOWNERS`.

| 현재 최종 풍량 | 발화 | 제안 결과 |
|---|---|---|
| 3단 | 1단으로 내려줘 | 1단 요청 허용, 안전 하한은 별도 유지 |
| 1단 | 2단으로 내려줘 | 방향 불일치, 상태 변경 없음 |
| 1단 | 3단으로 올려줘 | 3단 요청 허용 |
| 3단 | 3단으로 올려줘 | 이미 해당 단수, 무변경 |

[문서] 기본 프로파일은 인덕션 사용/주의 최소1단, 경고2단, 위험·고장3단이고 최종 풍량은 `max(fan_min, fan_requested)`다. 센서 미수집·경고 이상 부재 등의 추가3단 조건도 있다. 이 PR은 `profiles/`·Core·이 불변식을 변경하지 않는다. 근거: `profiles/default.json`, `safety_core/src/policy.cpp`의 최소 풍량·출력 계산.

[제안/합의 필요] 남현지(PM·Policy)·정정인(Core·계약)·임재범(계약·화면 영향)에게 아래를 요청한다. 아직 방향 필드를 보내거나 Core state 본문을 음성노드에서 해석하지 않는다.

1. 비교 기준을 최종 `fan.level`로 할지 사용자 요청 `fan.requested`로 할지. 사용자에게 보이는 최종 풍량 기준을 제안한다.
2. 안전 하한보다 낮은 목표는 거절할지 기존처럼 요청을 보존하고 보정할지. 같은 단수 요청의 무변경·이후 상태 영향도 함께 정한다.
3. 목표 단수+방향의 wire 표현, 수신 검증, 거절/무변경 결과 표시를 확정한다. 현행 FAN_SET(value)에는 방향이 없고 `additionalProperties:false`이므로 임의 필드를 보내지 않는다.
4. 스키마가 바뀌면 D-042/CLAUDE.md에 따라 스키마·예제·송신·수신·`v`와 이행 방식을 함께 검토한다. 승인 뒤 이수현이 음성 의미 추출/송신을 맞춘다.
