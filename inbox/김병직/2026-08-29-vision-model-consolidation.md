## 요약

카메라가 **HD-3000 USB 웹캠**으로 확정되면서, IMX500 AI Camera를 전제로 세운 고양이 검출 검증 계획은 그대로 실행할 수 없게 되었습니다.

대신 **ECO.AI 예제로 제공되는 YOLOX 하나로 사람과 고양이를 함께 검출**할 수 있습니다. COCO 80클래스 모델이라 `person`과 `cat`이 같은 추론 결과에서 나옵니다. 원본이 Apache-2.0이라 아직 미결인 AGPL 판단(`P-007`)을 우회할 수 있다는 이점도 있습니다.

역할 분담은 그대로 유지됩니다. 모델과 추론 루프만 공유하고 판정 로직은 각자 갖습니다.

---

## 2026-08-30 갱신 — 실기기 확인으로 바뀐 것

[Pi 4 · Pi 5 실기기 조사](2026-08-30-device-survey-and-vision-test.md)에서 확인한 내용입니다. **아래 세 가지가 이 문서의 전제를 바꿉니다.**

**① 플랫폼이 검출 모델을 내장 제공합니다 (선택지 추가).**

Pi 5의 `VisionService1`에 `person_detection`과 `obj_detect`이 등록돼 있습니다. **[문서]** 설정 파일이 가리키는 모델은 각각 `yolov11_det_w8a8.tflite`, `yolov8_det_w8a8.tflite`입니다.
→ 즉 "우리가 모델을 고른다"에 더해 **"플랫폼이 주는 것을 쓴다"**는 축이 하나 더 생겼습니다.

**② 그런데 그 내장 모델도 Ultralytics 계열입니다 — `P-007`이 우회되지 않습니다.**

이 문서 아래쪽에서 *"`P-006`의 선두 후보가 모두 YOLOv8n 계열이라 YOLOX 확정은 선두 후보를 배제하는 결과"*라고 적은 우려가, **플랫폼 내장 모델에도 그대로 적용됩니다.** 플랫폼 경로를 고르든 우리가 올리든 YOLOv8·YOLO11을 쓰는 한 `P-007` 판단이 필요합니다.
→ 다만 **플랫폼이 배포하는 것을 사용하는 경우 우리 배포 의무와 상황이 다를 수 있습니다.** **[추정]**이며 멘토 확인이 필요합니다 ([확인·결정 목록 B-5](2026-08-30-open-questions-and-decisions.md#b-멘토-문의-대장에-없음)).

**③ 사람과 고양이를 함께 잡으려면 `obj_detect`을 써야 합니다.**

**[문서]** `person_detection`은 decode 옵션이 `person_only#hard_classwise`라 **사람만 남기고 고양이를 걸러냅니다.** `obj_detect`은 `all#hard_classwise`로 80종 전부를 반환합니다.
→ 이 문서가 제안한 "한 모델로 통합"은 **`obj_detect` 쪽에서만 성립합니다.**

**아직 막혀 있는 것:** 두 모델 모두 **설정만 있고 파일이 기기에 없어** 현재는 실행되지 않습니다. YOLOX로 대체해 넣는 시험을 했으나 추론이 실행되지 않았고, 원인은 **[추정]** 백엔드 설정입니다. 자세한 내용은 [조사 문서 3장](2026-08-30-device-survey-and-vision-test.md#3-남은-문제-추정)에 있습니다.

**비전을 어느 보드에서 돌릴지**는 [P-009](../../docs/decision/P-009-pi4-pi5-role-reallocation.md)와 함께 정해야 합니다. `VisionService1`은 Pi 5에만 있습니다.

## 확인된 사실

### 하드웨어 구성

설계도 ② 최종 데모 구성 V4.0 기준입니다.

- 카메라는 **HD-3000 웹캠**이며 V4L2로 읽어 YOLO 입력으로 씁니다. AI 가속기가 내장된 카메라가 아닙니다.
- **Pi 4**가 센서·비전 노드입니다. Headless 프로파일, C++ 네이티브 서비스, YOLO 추론, I2C 센서 3종 폴링, MQTT 발행을 모두 담당합니다.
- **Pi 5**가 메인 노드입니다. Video 프로파일, Flutter UI, 판단 로직, 음성, MQTT 브로커를 담당합니다.
- Pi 4에는 NPU가 없습니다.

카메라 확정은 [Atlas AI 통합 의사결정 대장](../../docs/ai-integration-decisions.md)의 `P-001`(P0, "실제 카메라는 LifeCam HD-3000 USB UVC인가, IMX500 AI Camera인가?")에 대한 답이기도 합니다. 대장은 이 항목을 아직 미결로 두고 있으므로, 설계도 V4.0을 근거로 **HD-3000 확정**으로 닫을 것을 함께 제안합니다.

### ECO.AI YOLOX 예제

`AI-Native-OS-Samples/ecoai-tutorial`에 예제와 모델 내려받기 스크립트가 함께 들어 있습니다.

- 받을 수 있는 파일: ONNX(`float`, `w8a8`, `w8a8_mixed_int16`, `w8a16`), TFLite(`w8a8`)
- 출력 텐서 3개 — `boxes [1,N,4]`(xyxy), `scores [1,N]`, `class_idx [1,N]`
  **박스 디코딩이 모델 안에 이미 들어 있습니다.** 앵커·그리드 계산을 직접 구현할 필요가 없고, 코드가 하는 일은 점수 필터와 NMS뿐입니다.
- 클래스는 COCO 80종입니다. **`person = 0`, `cat = 15`, `dog = 16`**
- 전처리는 BGR→RGB 변환, 모델 입력 크기로 리사이즈, 255로 나누기입니다.
- 실행 옵션: `--backend cpu|gpu|gpu_cuda|htp_qnn`, `--threads N`, `--score`(기본 0.25), `--iou`(기본 0.45), `--warmup`(기본 50), `--runs N`
- **예제는 정지 이미지 한 장을 처리하고 끝납니다.** 웹캠 연속 처리 루프는 직접 만들어야 합니다.

### 사용 가능한 백엔드

통합 API가 받는 백엔드 이름은 `cpu` · `gpu` · `gpu_cuda` · `htp_qnn` 네 가지이고 기본값은 `cpu`입니다.

- `gpu_cuda`는 NVIDIA GPU 전용, `htp_qnn`은 퀄컴 NPU 전용이라 **Pi 4에서는 쓸 수 없습니다.**
- 따라서 실질적인 선택지는 **`cpu`(XNNPACK)** 이고, `gpu`(TFLite GPU delegate)가 Pi 4에서 실효가 있는지는 실측해 봐야 합니다.

### 기존 검증 계획과의 관계

[고양이 검출 모델 검증 계획](../이수현/2026-08-29-cat-detection-model-validation.md)의 1·2단계는 IMX500 전용 명령(`imx500_object_detection_demo.py`, `.rpk` 모델)이라 이 구성에서 실행되지 않습니다.

다만 그 문서가 스스로 조건을 달아 두었고, 지금 그 조건이 충족된 상황입니다.

> AI Camera가 아니라 일반 카메라라면 아래 IMX500 명령은 적용할 수 없다. Pi 4 CPU 단독 추론 또는 별도 가속기 경로를 다시 선정해야 한다.

문서의 나머지 부분 — 시험 데이터 구성표, 측정 항목과 통과 기준, 결과 기록표, 시간 필터 원칙 — 은 **모델과 무관하게 그대로 유효**합니다. 검증 방법론은 살리고 실행 경로만 바꾸면 됩니다.

## 결정 사항 (제안)

팀 승인이 필요한 제안입니다.

> **대장과의 관계.** 모델·런타임 선택은 [Atlas AI 통합 의사결정 대장](../../docs/ai-integration-decisions.md)의 `P-006`("최종 runtime/model은 무엇인가?")으로 이미 열려 있고 결정권자는 수현·정인입니다. 아래 1번은 그 항목을 대체하는 결정이 아니라 **`P-006`에 올리는 대안 후보**입니다. 대장에 기록된 기존 후보는 Atlas 내장 `YOLOv8 W8A8`(baseline), 외부 `YOLOv8n LiteRT W8A32`(정확도)와 `W8A8`(속도)입니다.

**1. 사람과 반려동물을 YOLOX 한 모델로 검출하는 안을 `P-006` 후보로 올립니다.**

추론을 한 번만 돌리고 `class_idx`로 갈라 씁니다.

```
YOLOX 추론 1회
   ├─ class 0  (person) → 조리구역 ROI    → 재실 판정 (Presence)
   └─ class 15 (cat)    → 인덕션 위험구역 ROI → 이상물체 판정
```

**2. 역할 분담은 유지합니다.** 모델 파일과 추론 루프는 공유하고, ROI 정의와 판정 로직은 각 담당이 따로 갖습니다. 검증도 각자의 기준으로 따로 합니다.

**3. IMX500 기반 실행 절차는 `deprecated`로 바꾸고 이 문서를 대체 문서로 연결합니다.** 검증 방법론 부분은 유지합니다.

**4. `ultralytics` YOLOv8n의 기기 탑재 여부는 `P-007` 결정을 따릅니다.** 라이선스 판단이 끝나기 전까지는 PC 프로토타입 전용으로 두기를 제안합니다.

4번은 주의가 필요합니다. `P-006`의 정확도·속도 선두 후보가 모두 YOLOv8n 계열이라, 이 제안을 그대로 확정하면 **선두 후보를 기기에서 배제하는 결과**가 됩니다. LiteRT로 변환한 artifact도 가중치 출처가 같아 AGPL 판단을 피해 가지 못합니다. 그래서 회의 안건은 "YOLOX로 바꾸자"가 아니라 **"YOLOX와 YOLOv8n을 같은 보드·같은 데이터로 비교하고 `P-007` 결과를 반영해 고른다"**가 되어야 합니다.

### 왜 합쳐야 하는가

취향의 문제가 아니라 **하드웨어 제약**입니다.

- Pi 4 CPU에서 검출 모델 두 개를 동시에 돌릴 여유가 없습니다. NPU가 없어 백엔드가 CPU 하나뿐입니다.
- 같은 Pi 4가 I2C 센서 3종 폴링과 MQTT 발행도 함께 합니다.
- 데모 구성도에 **케이스 팬이 필수**로 적혀 있습니다. 발열과 스로틀링이 이미 예상되는 상황입니다.

### 라이선스 — `P-007` 해소에 도움이 됩니다

라이선스 수용 여부는 대장의 `P-007`("Ultralytics AGPL-3.0 조건을 수용할 수 있는가?")이고 **결정권자는 현지, 법적 판단은 미완료**입니다. 아래는 그 판단에 넣을 재료이지 결론이 아닙니다.

- `ultralytics` YOLOv8n·YOLO11n은 **AGPL-3.0**이라 배포 형태에 제약이 있습니다. 기존 문서에서도 이 점이 지적되어 있었습니다.
- **YOLOX 원본은 Apache-2.0**(Megvii)입니다. YOLOX를 고르면 `P-007`을 닫지 않고도 진행할 수 있습니다.
- 추가로, `ultralytics`는 최초 실행 시 모델을 인터넷에서 내려받습니다. 데모 환경이 Wi-Fi를 끈 폐쇄 LAN이라 **온디바이스·오프라인 원칙과도 맞지 않습니다.**

## 검증 계획 (기기 도착 후)

예제에 벤치마크 기능이 내장되어 있어 별도 도구가 필요 없습니다.

```
--runs N --warmup 50
```

### 모델 비교

| 모델 파일 | 목적 |
|---|---|
| `yolox-onnx-float` | 정확도 기준선 |
| `yolox-tflite-w8a8` | CPU에서 가장 빠를 것으로 예상 |
| `yolox-onnx-w8a8` | 위 둘의 중간 확인 |
| `yolox-onnx-w8a16` | 정확도 손실이 클 때 대안 |

`--threads`는 1 / 2 / 3으로 나눠 측정합니다. Pi 4는 4코어지만 센서 폴링이 함께 도므로 전부 쓰면 안 됩니다.

### 통과 기준

**합격선은 2 FPS입니다.**

근거는 판정 로직에서 나옵니다. 비전 노드가 1초마다 heartbeat를 보내고 단계 상승 조건이 N초(3~5초 제안) 연속 유지이므로, 그 시간 안에 판정에 쓸 프레임이 여러 장 있어야 합니다. 2 FPS면 3초 창에 6프레임이 잡힙니다.

**1 FPS 미만이면 모델을 더 줄이거나 판정 로직을 다시 설계해야 합니다.**

**1~2 FPS 구간은 아직 정하지 못했습니다.** 3초 창에 3~6프레임이라 판정에 빠듯해지는 구간입니다. 실측값이 여기 들어오면 N초 조건을 늘릴지 모델을 바꿀지 회의에서 정해야 합니다.

정확도 항목(Recall, 오검출률, 안정 검출 시간, 끊김)과 시험 데이터 구성은 기존 고양이 검출 문서의 표를 그대로 씁니다.

## 미리 알아둘 리스크

**전처리가 레터박스가 아니라 단순 리사이즈입니다.**

예제는 `cv::resize`로 모델 입력 크기에 맞춥니다. HD-3000이 4:3 또는 16:9인데 모델 입력이 정사각형이면 **화면이 가로로 눌립니다.** 사람은 세로로 긴 형상이라 이 왜곡에 민감할 수 있습니다.

정확도가 예상보다 낮게 나오면 여기를 먼저 의심하고, 레터박스 전처리로 바꿔 재측정합니다. 이때 좌표 복원식도 함께 고쳐야 합니다.

## 미확인 사항

- ECO.AI로 직접 추론할지, 플랫폼 비전 서비스를 거칠지 (별도 문서에서 다룹니다)
- Headless 네이티브 서비스가 카메라 장치에 직접 접근할 수 있는지 — 멘토 확인 필요
- ECO.AI 배포본의 YOLOX 라이선스 표기 — 모델 파일을 받을 때 함께 확인
- 실제 설치 높이와 화각. 카메라를 후드에 달아 내려다보면 **발끝 기준 ROI 판정이 성립하지 않습니다.** 사람 인식 판정 로직의 전제라 먼저 확인해야 합니다
- 조리구역 ROI와 위험구역 ROI의 실제 좌표
- `person` 검출 결과를 실을 topic·schema가 없습니다. [`contracts/cat-detection.schema.json`](../../contracts/cat-detection.schema.json)은 `label`이 `const "cat"`인 고양이 전용이라, 추론 1회에서 함께 나온 person 결과의 발행 경로를 따로 정해야 합니다
- HD-3000의 저조도 성능. 검증 항목에 저조도가 있는데 고정초점 웹캠이라 확인이 필요합니다
