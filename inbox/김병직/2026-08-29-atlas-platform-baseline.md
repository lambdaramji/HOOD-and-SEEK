## 요약

이 프로젝트는 **ATLAS(AI-native OS)** 위에서 개발합니다. README의 「Atlas AI 통합 상태」 절과 AGENTS.md가 ATLAS를 언급하지만, 둘 다 모델·런타임 선택 이야기입니다. **개발 플랫폼으로서의 ATLAS — 프로파일, D-Bus, 빌드 타깃 — 는 아직 어디에도 정리돼 있지 않아**, 저장소만 읽는 사람은 일반 Raspberry Pi + Python 프로젝트로 오해하게 됩니다.

보드는 **두 대이고 역할이 다릅니다.** Pi 4는 Headless 프로파일로 센서·비전을, Pi 5는 Video 프로파일로 UI·판단을 맡습니다.

**2026-08-30 갱신:** 아래 「멘토에게 확인할 것」의 Pi 5 이미지 항목은 **해결되었습니다.** 실기기 확인 결과는 [Pi 4 · Pi 5 실기기 조사](2026-08-30-device-survey-and-vision-test.md)에 있으며, 이 문서에서 갱신이 필요한 부분은 그 문서 4장에 표로 정리했습니다.

> **자료 취급 주의.** 배포받은 개발 문서에는 기밀 표기가 있습니다. 이 문서에는 **원문을 옮기지 않고**, 어느 문서에 무엇이 있는지와 우리 팀이 내린 결론만 적습니다. PDF 자체는 저장소에 올리지 않습니다.

### 대회에서 쓰는 프로파일

플랫폼은 기능을 프로파일 단위로 묶고, 하위 프로파일 위에 기능을 더해 가는 구조입니다.

`Essential → Headless → Graphical → Video`

**이번 대회는 Headless와 Video를 씁니다.** 보드가 두 대인 구성과 정확히 맞습니다.

| 보드 | 프로파일 | 역할 |
|---|---|---|
| Raspberry Pi 4 | Headless | 센서·비전 노드. C++ 네이티브 서비스, YOLO 추론, I2C 센서 3종, MQTT 발행 |
| Raspberry Pi 5 (8GB) | Video | 메인 노드. Flutter UI, 판단 로직, 음성, MQTT 브로커, 터치스크린 |

두 보드는 유선 이더넷 폐쇄 LAN에서 MQTT로 통신합니다.

### 비전 실행 경로는 두 축으로 나눠 정합니다

처음에는 「플랫폼 서비스 vs ECO.AI」의 택일로 적었으나, 이는 성립하지 않는 대립 구도입니다. 저장소에 이미 병합된 [Atlas AI 기술 의사결정 및 통합 검증 보고서](../../docs/atlas-ai-decision-and-validation-report.md) 2.2절이 같은 점을 지적하고 있어 그 구분을 따릅니다.

**축 1 — 통합 위치: 누가 카메라·세션·자원을 관리하는가**

- **플랫폼 서비스 경로 (`VisionService1`)** — 세션을 만들고 시작·정지하는 구조입니다. 모델 이름, 프레임 소켓 경로, 포맷, 해상도를 넘겨 세션을 만들고 결과는 시그널로 받습니다. 기기에 어떤 모델이 들어 있는지 조회하는 메서드도 있습니다. 권한이 **사용자 동의(user_consent)** 등급입니다.
- **앱·서비스 직접 경로** — 개발 PC에서 크로스 컴파일 → 기기로 복사 → 실행하는 흐름입니다. 카메라 접근과 lifecycle을 직접 관리해야 합니다.

**축 2 — 추론 런타임: 누가 텐서 연산을 실행하는가**

ECO.AI는 이 축의 후보이고, 그 자체가 런타임이 아니라 **TensorFlow Lite · ONNX Runtime · ExecuTorch를 통합 API 하나로 감싼 계층**입니다. 그래서 축 1에서 어느 쪽을 고르든 그 아래에 놓일 수 있고, 「VisionService 대 ECO.AI」로 맞세울 대상이 아닙니다. TFLite·ONNX Runtime을 직접 쓰는 선택지도 같은 축에 있습니다.

현재 데모 구성도는 **축 1의 직접 경로 + 축 2의 ECO.AI**에 가깝습니다. 모델 후보와 근거는 [사람·반려동물 검출 모델 통합 제안](2026-08-29-vision-model-consolidation.md)에 정리했습니다.

### 카메라 권한

카메라 인터페이스의 열기·스트리밍 시작이 **사용자 동의 등급**입니다.

→ **최초 1회 동의 절차를 시연 순서에 포함해야 합니다.** 시연 당일 예상 못 한 동의 창이 뜨면 곤란합니다.

### 사용 가능한 백엔드

통합 API가 받는 이름은 `cpu` · `gpu` · `gpu_cuda` · `htp_qnn` 네 가지이고 기본값은 `cpu`입니다.

`gpu_cuda`는 NVIDIA, `htp_qnn`은 퀄컴 전용이라 **Pi 4에서는 `cpu`(XNNPACK)가 사실상 유일한 선택지**입니다.

**[회신 2026-09-03 결론]** Pi 4에서는 TFLite GPU 백엔드가 CPU보다 약 5배 느려 XNNPACK(CPU)이 권장이므로 **이 판단이 확정됐습니다.** Pi5는 TFLite의 경우 GPU가 권장입니다(OpenCL은 없지만 OpenGL로 fallback). → [LG 회신 검토](../임재범/2026-09-03-lg-answer-review.md)

### 문서에 명세가 없는 부분

ECO.AI 레퍼런스의 「모델 입출력 명세」 표에는 MobileNet V2, EfficientNet B0, DeepLabV3+, Llama 네 종만 있습니다. **우리가 쓸 YOLOX는 이 표에 없습니다.**

예제 코드와 모델 내려받기 스크립트, 실행 명령 예시는 모두 제공되므로, **YOLOX의 입출력 명세는 예제 코드가 유일한 출처**입니다. 확인한 내용은 검출 모델 문서에 정리해 두었습니다.

3. 실행 경로는 **축 1(통합 위치: 플랫폼 서비스 vs 직접 경로)부터** 정합니다. 축 2(추론 런타임)는 그 뒤에 정해도 늦지 않습니다. 축 1이 정해지기 전에는 판단 로직 담당이 코드를 어느 쪽으로 짤지 알 수 없습니다.

**대신 확인된 새로운 사실 — 비전 서비스가 보드마다 다릅니다.**

| | Pi 4 | Pi 5 |
|---|---:|---:|
| `com.atlas.*` 서비스 수 | 30 | 53 |
| `VisionService1` | **없음** | 있음 |
| `VoiceManager1` | 없음 | 없음 |

이 문서 위쪽 「비전 실행 경로가 두 가지입니다」 절은 **Pi 5에 한해서만 성립합니다.** Pi 4에서는 플랫폼 비전 서비스를 쓸 수 없고 ECO.AI 직접 사용만 가능합니다.

**[회신 2026-09-03] 이제 Pi 5에서도 성립하지 않습니다.** LG는 `VisionService`를 RPi5 미지원 인터페이스로 회신했습니다. **두 보드 모두 직접 경로만 남습니다.** → [LG 회신 검토](../임재범/2026-09-03-lg-answer-review.md)

이 사실은 [P-009 · Pi4/Pi5 역할 재배치](../../docs/decision/P-009-pi4-pi5-role-reallocation.md) 결정의 근거가 됩니다. 자세한 내용은 [실기기 조사 5장](2026-08-30-device-survey-and-vision-test.md#5-p-009에-대한-실측-근거)에 있습니다.

### ★ 비전 모델 파일과 백엔드 설정 (신규 · 최우선)

Pi 5의 `VisionService1`에 `person_detection`·`obj_detect` 모델이 **설정만 있고 파일이 없습니다.** 또한 백엔드가 퀄컴 NPU 전용(`NPU_QNN_HTP`)으로 잡혀 있습니다.

**[회신 2026-09-03] 두 항목 모두 답을 받았고, 결함이 아닙니다.**

- 모델 파일 부재는 **배포 누락이 아닙니다.** `GetSupportedModels`가 돌려주는 것은 LG가 내부에서 동작을 시험한 모델 목록이고, 원본 모델은 별도 제공 대상이 아닙니다.
- `NPU_QNN_HTP`는 **퀄컴 전용이라 Pi5에서 쓸 수 없는 백엔드**입니다. Pi5는 GPU가 권장이므로 `GPU`로 바꾼 조치가 권장 설정과 일치합니다.
- 다만 **`VisionService` 자체가 RPi5 미지원**이라는 회신이 함께 왔으므로 **이 절의 경로는 더 이상 권장 경로가 아닙니다.** → [LG 회신 검토](../임재범/2026-09-03-lg-answer-review.md)

문의할 내용은 [확인·결정 목록 B-1~B-4](2026-08-30-open-questions-and-decisions.md#b-멘토-문의-대장에-없음)에 정리했습니다.

### 함께 물어볼 것

- MQTT 브로커(mosquitto)를 기기에 설치할 수 있는지
- Headless 네이티브 서비스가 카메라 장치에 직접 접근할 수 있는지 (플랫폼 카메라 서비스를 거치지 않는 방식)
- 서비스 유휴 자동 종료를 설정으로 끌 수 있는지 — **안전 판단 서비스는 상시 떠 있어야 합니다.** 주기적 통신으로 우회할 수도 있지만 설정으로 해결하는 편이 정공법입니다
